## Overview

Like class models, data models define behavior (actions/views) over observable data. Unlike class models, they keep the underlying data plain: snapshots do not gain a `$modelType` field. This tradeoff has a few consequences:

- The model instances are created lazily and when needed rather than eagerly.
- The only life-cycle hook, `onLazyInit`, runs the first time the wrapper for a data node is created. Reusing that wrapper preserves its instance fields and does not rerun the hook. If initialization throws, a later construction attempt retries initialization.
- Reconciliation is somewhat worse due to the lack of an ID property to uniquely identify the instances.

Data models are therefore a good fit for backend-shaped payloads that must remain free of library metadata while being edited locally and eventually sent back.

## Your first data model

Data models are defined much like [class models](./classModels.mdx), except that they extend `DataModel` instead of `Model`:

<Tabs groupId="prop-kind">
<TabItem value="prop" label="prop">

```ts title="Todo.ts"
@model("myCoolApp/Todo")
// highlight-next-line
export class Todo extends DataModel({
  text: prop<string>(), // required
  done: prop(false), // defaults to `false`
}) {
  @modelAction
  setDone(done: boolean) {
    this.done = done
  }

  @modelAction
  setText(text: string) {
    this.text = text
  }

  @computed
  get asString() {
    return `${!this.done ? "TODO" : "DONE"} ${this.text}`
  }
}
```

</TabItem>
<TabItem value="tProp" label="tProp">

```ts title="Todo.ts"
@model("myCoolApp/Todo")
// highlight-next-line
export class Todo extends DataModel({
  text: tProp(types.string), // required
  done: tProp(types.boolean, false), // defaults to `false`
}) {
  @modelAction
  setDone(done: boolean) {
    this.done = done
  }

  @modelAction
  setText(text: string) {
    this.text = text
  }

  @computed
  get asString() {
    return `${!this.done ? "TODO" : "DONE"} ${this.text}`
  }
}
```

</TabItem>
</Tabs>

Properties are declared with `prop` / `tProp` in the same way as in class models; see [property declarations](./classModels.mdx#property-declarations).

:::note
Property defaults are applied only when wrapping a plain object with `new`, not when wrapping an existing tree node.
:::

## Data model rules

- Decorate the class with `@model` and give the model type a unique application-wide name.
- Extend `DataModel` with the properties that should be observable, snapshotable, and patchable.
- Access model data through either `this` or `this.$`.
- Change model data inside model actions.

:::warning No constructors
Do not declare a constructor in a data model. Use [`onLazyInit`](#life-cycle-event-hooks) when initialization logic is needed.
:::

Of course primitives are not the only kinds of data that a data model can hold. Arrays, plain objects, and other objects can be used as well.

:::warning Insert the data, not the model
Data models are wrappers around actual data object nodes. Creating an instance with `new` creates a wrapper over the data node (or over a new data node if the input was not one). That means the model itself can't be inserted into a tree; insert the wrapped data instead, which is available as `model.$`.
:::

## Creating a data model instance

An instance of the todo data node plus its wrapper model can be created like this:

```ts
const myTodo1 = new Todo({ done: true, text: "buy some milk" })
// `myTodo1.$` will hold the data object that can be inserted into a tree
```

Note that if the input data is a tree node then `myTodo1.$` will be exactly that same data tree node passed in the constructor.
If it is not a tree node then `myTodo1.$` will be the `toTreeNode` version of the passed data object.
Also, multiple calls to `new` over a same data tree node will return the same model instance every time.

In practice, you usually pass the data node around and create its wrapper with `new` only when you need the model's behavior.

Some examples:

```ts
const todoList: ModelData<Todo>[] = [...];
// usually we would use `todoList[x]` to access the data ...

// until the moment we want to edit a particular todo
const editableTodo = new Todo(todoList[x]);
editableTodo.setText("hi there")
// once done we can just "throw away" the editable instance
```

```ts
const todoList: ModelData<Todo>[] = [...];

const newTodo = new Todo({ done: false, text: "" })
// ...
newTodo.setText("buy milk")
// note how we insert into the tree the data, not the model itself!
todoList.push(newTodo.$);
```

## Automatic data model actions for property setters

Most times, the only action we need for a property is a setter. We can use the prop modifier `withSetter()` (`withSetter("assign")` has been deprecated) to reduce boilerplate and generate property setters. For example, the model above could be written as:

```ts
@model("myCoolApp/Todo")
export class Todo extends DataModel({
  text: prop<string>().withSetter(),
  done: prop<boolean>().withSetter(),
}) {}

const myTodo = new Todo({ text: "buy some coffee", done: false })

// this is now allowed and properly wrapped in two respective actions
myTodo.setText("buy some milk")
myTodo.setDone(true)
```

If you need to change data without declaring a custom `modelAction`, use the predefined `objectActions` or `arrayActions` helpers.

`withSetter` also accepts a value transform function. For example `withSetter(cloneTreeValue)` clones incoming non-primitive values before setting them, which is useful when the same object instance may be reused across different places in the tree. If you need clone options, wrap it (for example `withSetter((x) => cloneTreeValue(x, { generateNewIds: false }))`).

:::note
The transform function only runs in the generated setter (for example `model.setX(3)`). It does **not** run during model construction (`new Model({ x: 3 })`) or snapshot deserialization, where the value is assigned as provided.
:::

## Life-cycle event hooks

Data models only support a single limited life-cycle event hook:

- `onLazyInit()`, which is called the first time `new` is called to wrap a certain data node in the life-time of the application.

If you need something that runs more consistently consider using `onChildAttachedTo` over the data node parent itself.

## Runtime data

Runtime data that does not need to be snapshotted can be declared as a regular class property. Use MobX decorators when that runtime data also needs to be observable.

```ts
@model("myApp/SomeModel")
class SomeModel extends DataModel({
  title: prop("demo"),
}) {
  // non-observable runtime data
  saveCount = 0

  markSaved() {
    this.saveCount++
  }

  // or observable in the usual MobX way
  @observable
  isSaving = false

  @action
  setSaving(isSaving: boolean) {
    this.isSaving = isSaving
  }
}
```

Note that this runtime data holds to the same lazy creation rules as the data model wrapper instance itself.

## Getting the TypeScript types for model data

- `ModelData<Model>` is the type of the model props without transformations (as accessible via `model.$`).

For example `ModelData<Todo>` would return `{ text: string; done: boolean; }`.

## Flows (async actions)

While `@modelAction` defines sync model actions, async model actions are possible as well with the use of `@modelFlow`. A flow is a generator function where `yield* _await(x)` takes the place of `await x`:

<Tabs groupId="language">
<TabItem value="ts" label="TypeScript">

```ts
interface Book {
  title: string
  price: number
}

@model("myApp/BookStore")
class BookStore extends DataModel({
  books: prop<Book[]>(() => []),
}) {
  @modelFlow
  // highlight-next-line
  fetchMyBooksAsync = _async(function* (this: BookStore, token: string) {
    // highlight-next-line
    const myBooks = yield* _await(myBackendClient.getBooks(token))
    this.books = myBooks
  })
}
```

In TypeScript, wrap the generator in `_async` and type `this` as the class, so the flow is typed as returning a promise.

</TabItem>
<TabItem value="js" label="JavaScript">

```js
@model("myApp/BookStore")
class BookStore extends DataModel({
  books: prop(() => []),
}) {
  @modelFlow
  // highlight-next-line
  *fetchMyBooksAsync(token) {
    // highlight-next-line
    const myBooks = yield* _await(myBackendClient.getBooks(token))
    this.books = myBooks
  }
}
```

</TabItem>
</Tabs>

In either case it is called like any async function:

```ts
const myBookStore = new BookStore({})
await myBookStore.fetchMyBooksAsync("someToken")
```

:::warning `yield*`, not `yield`
Always use `yield* _await(...)`. `_await` only works when delegated to with `yield*`, and a plain `yield` does not work.
:::

## Factory pattern / Generics

If you are _not_ relying on `tProp` to do runtime type checking it is possible to use this pattern to get generic classes:

```ts
@model("myApp/GenericPoint")
class GenericPoint<T> extends DataModel(<T>() => ({
  x: prop<T>(),
  y: prop<T>(),
}))<T> {
  @modelAction
  setXY(x: T, y: T) {
    this.x = x
    this.y = y
  }
}

@model("myApp/Generic3dPoint")
class Generic3dPoint<T> extends ExtendedDataModel(<T>() => ({
  baseModel: modelClass<GenericPoint<T>>(GenericPoint),
  props: {
    z: prop<T>(),
  },
}))<T> {
  // ...
}
```

If you rely on `tProp` (and also `prop` really) a different possibility is to use a factory pattern with data models. For example:

```ts
function createModelClass<TX, TY>(modelName: string, initialX: TX, initialY: TY) {
  @model(`myApp/${modelName}`)
  class MyModel extends DataModel({
    x: prop<TX>(() => initialX),
    y: prop<TY>(() => initialY),
  }) {
    @modelAction
    setXY(x: TX, y: TY) {
      this.x = x
      this.y = y
    }
  }

  return MyModel
}

const NumberMyModel = createModelClass("NumberMyModel", 10, 20)
type NumberMyModel = InstanceType<typeof NumberMyModel>

const numberMyModelInstance = new NumberMyModel({}) // this will be of type `NumberMyModel`
numberMyModelInstance.setXY(50, 60)

const StringMyModel = createModelClass("StringMyModel", "10", "20")
type StringMyModel = InstanceType<typeof StringMyModel>

const stringMyModelInstance = new StringMyModel({}) // this will be of type `StringMyModel`
stringMyModelInstance.setXY("50", "60")
```

Note that the above will only work when not generating declaration maps. If you need to generate declarations (for example for a library) then it is a bit more tedious, but still possible:

```ts
export function createModelClass<TX, TY>(modelName: string, initialX: TX, initialY: TY) {
  const MyModelProps = DataModel({
    x: prop<TX>(() => initialX),
    y: prop<TY>(() => initialY),
  })

  @model(`myApp/${modelName}`)
  class MyModel extends MyModelProps {
    @modelAction
    setXY(x: TX, y: TY) {
      this.x = x
      this.y = y
    }
  }

  return MyModel as ModelClassDeclaration<
    typeof MyModelProps,
    {
      setXY(x: TX, y: TY): void
    }
  >
}
```

## Inheritance

Model inheritance is possible with a few gotchas.

The first thing to bear in mind is that data models that extend from other data models must use `ExtendedDataModel` rather than the plain `DataModel`. For example:

```ts
@model("MyApp/Point")
class Point extends DataModel({
  x: prop<number>(),
  y: prop<number>(),
}) {
  get sum() {
    return this.x + this.y
  }
}

// note how `ExtendedDataModel` is used
@model("MyApp/Point3d")
class Point3d extends ExtendedDataModel(Point, {
  z: prop<number>(),
}) {
  get sum() {
    return super.sum + this.z
  }
}
```

Also, remember that if your base model has `onLazyInit` and you redeclare it in your extended model you will need to call `super.onLazyInit(...)` in the extended model.

When extending a generic class, use `modelClass` to specify the concrete generic type:

```ts
class X extends ExtendedDataModel(modelClass<SomeGenericClass<string>>(SomeGenericClass), { ... }) { ... }
```

If you don't it will still compile, but the generic will be assumed to have `unknown` for all its generic parameters.

## Usage without decorators

Although this library was primarily intended to be used with decorators it is also possible to use it without them.

To do so you can use the `decoratedModel` function as shown below:

```ts
// note the `_` at the beginning of the name to distinguish it from the decorated version
class _Todo extends DataModel({
  text: prop<string>(),
  done: prop<boolean>(),
}) {
  // note how here we don't decorate the method directly, but on the next parameter instead
  // @modelAction
  setDone(done: boolean) {
    this.done = done
  }

  // @modelAction
  setText(text: string) {
    this.text = text
  }

  // @computed
  get fullText() {
    return `${this.done ? "DONE" : "TODO"} - ${this.text}`
  }
}

const Todo = decoratedModel(
  // the string identifies this model type and must be unique across your whole application
  // you may pass `undefined` if you don't want the model to be registered yet (e.g. for a base class)
  "myCoolApp/Todo",
  _Todo,
  // here we pass what we would use as decorators to the class methods/properties above
  // if we want to use multiple chained decorators we can pass an array of them instead
  // note that any kind of TypeScript-compatible decorator is supported, not only the built-in ones!
  {
    setDone: modelAction,
    setText: modelAction,
    fullText: computed,
  }
)
// needed to be able to do `SnapshotInOf<Todo>`, type a variable as `Todo`, etc
type Todo = _Todo
// if `_Todo` was generic then it would be `type Todo<T> = _Todo<T>`

const myTodo = new Todo({ done: false, text: "buy some milk" })
```
