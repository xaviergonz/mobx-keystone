<p className="docs-intro-lead">`mobx-keystone` takes many of its ideas from `mobx-state-tree`, so most concepts carry straight over. The differences are in how models are typed, how snapshots and instances mix, and how predictable the model life-cycle is.</p>

<div className="docs-starting-links">

[**Plain TypeScript types →**<span>Type models with standard annotations. Runtime types are opt-in.</span>](#typescript)
[**No snapshot / instance casts →**<span>Properties hold instances, and snapshots stay at the edges.</span>](#snapshot-instance-types)
[**`this` everywhere →**<span>Class models with standard MobX `computed` decorators.</span>](#this-and-computed)
[**Predictable life-cycle →**<span>Two hooks that always run when you expect them to.</span>](#life-cycle)

</div>

## Feature by feature

<div className="docs-compare-table">

| Feature | `mobx-keystone` | `mobx-state-tree` |
| --- | --- | --- |
| Tree-like structure | <span className="docs-compare-yes">Yes</span> <small>Class models, data models, and plain objects / arrays.</small> | <span className="docs-compare-yes">Yes</span> <small>Models built with <code>types.model</code>.</small> |
| Immutable snapshot generation | <span className="docs-compare-yes">Yes</span> <small><code>getSnapshot</code>, with structural sharing.</small> | <span className="docs-compare-yes">Yes</span> <small><code>getSnapshot</code>, with structural sharing.</small> |
| Patch generation | <span className="docs-compare-yes">Yes</span> <small><code>onPatches</code> / <code>applyPatches</code>, with inverse patches.</small> | <span className="docs-compare-yes">Yes</span> <small><code>onPatch</code> / <code>applyPatch</code>, with reverse patches.</small> |
| Action serialization / replaying | <span className="docs-compare-yes">Yes</span> <small><code>onActionMiddleware</code> / <code>applySerializedActionAndTrackNewModelIds</code>, ready for server sync.</small> | <span className="docs-compare-yes">Yes</span> <small><code>onAction</code> / <code>applyAction</code>.</small> |
| Action middlewares | <span className="docs-compare-better">Better</span> <small><code>actionTrackingMiddleware</code> makes async (flow) middlewares easier to write.</small> | <span className="docs-compare-yes">Yes</span> <small><code>addMiddleware</code>.</small> |
| Transaction middleware | <span className="docs-compare-yes">Yes</span> <small><code>transactionMiddleware</code> or the <code>@transaction</code> decorator.</small> | <span className="docs-compare-yes">Yes</span> <small><code>atomic</code>, from <code>mst-middlewares</code>.</small> |
| Undo manager middleware | <span className="docs-compare-yes">Yes</span> <small><code>undoMiddleware</code>, built in, with grouping and attached state.</small> | <span className="docs-compare-yes">Yes</span> <small><code>UndoManager</code>, from <code>mst-middlewares</code>.</small> |
| Flow (async) actions | <span className="docs-compare-yes">Yes</span> <small><code>@modelFlow</code>, fully typed through <code>_async</code> / <code>_await</code>.</small> | <span className="docs-compare-yes">Yes</span> <small><code>flow</code> generators.</small> |
| References | <span className="docs-compare-yes">Yes</span> <small><code>rootRef</code> / <code>customRef</code>, plus back-references with <code>getRefsResolvingTo</code>.</small> | <span className="docs-compare-yes">Yes</span> <small><code>types.reference</code> / <code>types.safeReference</code>.</small> |
| Frozen data | <span className="docs-compare-yes">Yes</span> <small><code>frozen</code>.</small> | <span className="docs-compare-yes">Yes</span> <small><code>types.frozen</code>.</small> |
| TypeScript support | <span className="docs-compare-better">Much better</span> <small>Self and cross-model references, no late types, no casts.</small> | <span className="docs-compare-yes">Yes</span> <small>Needs <code>types.late</code>, casts, and <code>Instance</code> / <code>SnapshotIn</code> helpers.</small> |
| Simple instance / snapshot types | <span className="docs-compare-yes">Yes</span> <small>Properties hold instances. Snapshots stay at the edges.</small> | <span className="docs-compare-no">No</span> <small>Properties accept both, so assignments often need <code>cast</code>.</small> |
| Simple model life-cycle | <span className="docs-compare-yes">Yes</span> <small><code>onInit</code> and <code>onAttachedToRootStore</code>, never lazy.</small> | <span className="docs-compare-no">No</span> <small>Four hooks, which lazy node creation can delay or skip.</small> |
| Runtime type validation | <span className="docs-compare-yes">Yes</span> <small>Completely optional.</small> | <span className="docs-compare-yes">Yes</span> <small>Built into the model types.</small> |
| No metadata inside snapshots | <span className="docs-compare-yes">Yes</span> <small>Only with data models, which have no life-cycle hooks.</small> | <span className="docs-compare-better">Better</span> <small>Snapshots are always plain data.</small> |
| Redux compatibility layer | <span className="docs-compare-yes">Yes</span> <small><code>asReduxStore</code> and <code>connectReduxDevTools</code>.</small> | <span className="docs-compare-yes">Yes</span> <small><code>asReduxStore</code> and <code>connectReduxDevtools</code>.</small> |

</div>

## TypeScript improvements {#typescript}

`mobx-state-tree` has some limitations when it comes to TypeScript typings, which `mobx-keystone` tries to overcome.

### If you know TypeScript you already know how to type models

When not using runtime type checking, `mobx-keystone` uses standard TypeScript type annotations to declare model data, which lowers the learning curve.
If you do need runtime type checking, `mobx-keystone` also includes a completely optional type definition / runtime type checking system.

### Self-recursive and cross-referenced models

Self-recursive or cross-referenced models are impossible (or at least very hard) to properly type in `mobx-state-tree`, but they become trivial with `mobx-keystone`.

```ts title="mobx-keystone"
// self recursive model
@model("myApp/TreeNode")
class TreeNode extends Model({ children: prop<TreeNode[]>(() => []) }) {}

// cross-referenced models
@model("myApp/A")
class A extends Model({ b: prop<B | undefined>() }) {}

@model("myApp/B")
class B extends Model({ a: prop<A | undefined>() }) {}
```

### Simpler instance / snapshot type usage {#snapshot-instance-types}

In `mobx-state-tree` you can assign both snapshots and instances to properties, but the properties are typed as instances. That leads to confusing casts and constructs such as:

<div className="docs-code-compare">

```ts title="mobx-state-tree"
const Todo = types
  .model({
    done: false,
    text: types.string,
  })
  .actions((self) => ({
    setText(text: string) {
      self.text = text
    },
    setDone(done: boolean) {
      self.done = done
    },
  }))

const RootStore = types
  .model({
    selected: types.maybe(Todo),
  })
  .actions((self) => ({
    // note the union of the snapshot type and the instance type
    setSelected(todo: SnapshotIn<typeof Todo> | Instance<typeof Todo>) {
      // note the cast to say it is ok to use a snapshot when
      // the property actually expects an instance
      self.selected = cast(todo)
    },
  }))
```

In `mobx-keystone`, snapshots usually only show up when calling `getSnapshot` and `fromSnapshot`, so the same code gets simpler:

```ts title="mobx-keystone"
@model("myApp/Todo")
class Todo extends Model({
  done: prop(false).withSetter(),
  text: prop<string>().withSetter(),
}) {}

@model("myApp/RootStore")
class RootStore extends Model({
  selected: prop<Todo | undefined>(undefined).withSetter(),
}) {}
```

</div>

### Less confusion between `this` and `self`, plus standard computed decorators {#this-and-computed}

In `mobx-state-tree`, code from a previous "chunk" (actions, views) usually has to be accessed through `self`, while code in the same chunk has to be accessed through `this` to get proper typings:

<div className="docs-code-compare">

```ts title="mobx-state-tree"
const Todo = types
  .model({
    done: false,
    text: types.string,
    title: types.string,
  })
  .views((self) => ({
    get asStr() {
      // `self`, since the properties come from a previous chunk
      return `${self.text} is done? ${self.done}`
    },
    get asStrWithTitle() {
      // `this` for `asStr`, since it comes from the current chunk
      return `${self.title} - ${this.asStr}`
    },
  }))
```

In `mobx-keystone`, `this` always works, and you use the standard MobX `computed` decorator (including its extra options):

```ts title="mobx-keystone"
@model("myApp/Todo")
class Todo extends Model({
  done: prop(false),
  text: prop<string>(),
  title: prop<string>(),
}) {
  @computed
  get asStr() {
    return `${this.text} is done? ${this.done}`
  }

  @computed
  get asStrWithTitle() {
    return `${this.title} - ${this.asStr}`
  }
}
```

</div>

## Simplified model life-cycle {#life-cycle}

`mobx-state-tree` has several life-cycle hooks (`afterCreate`, `afterAttach`, `beforeDetach`, `beforeCreate`) that might or might not trigger when you think they should, due to the lazy initialization of nodes.

- A submodel with an `afterCreate` hook might never run it unless the node contents are accessed.
- You might want to set up an effect (a `reaction` or the like) only once the model is actually part of your application state.
- `getRoot` might not return the root you expect until the model is attached to a parent that is eventually (or never) attached to the proper root.

`mobx-keystone` solves this by offering only two life-cycle hooks:

<div className="docs-compare-table">

| Hook                    | When it runs                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `onInit`                | _Always_, once the model has been created. There is no lazy initialization.                                              |
| `onAttachedToRootStore` | Once the model is attached to a root store, so `getRoot` returns the expected value. It can return a disposer that runs when the model is detached, which makes it the perfect place to set up effects. |

</div>
